# 技术设计：X Layer xStocks LP 激励自动化系统

## 1. 设计约束

| 约束 | 来源 | 对设计的影响 |
|---|---|---|
| 活动窗口约两周 | 官方档期 | 拒绝重基建（不自建索引器/RPC），优先可用性 |
| 奖励按小时结算、按手续费份额分配 | 活动规则 | 目标函数是 in-range 份额，uptime 是一级指标 |
| 出界即当小时归零 | Uniswap 机制 | 再平衡必须低延迟；宁可略宽也不能失联 |
| 标的是美股，7×24 链上交易 | xStocks | 必须有交易日历与事件日历；波动率分时段建模 |
| 涉及真实资金且规则存在未知项 | 事实清单 F1–F10 | dry-run 为默认；未核实项阻塞实盘 |
| 多人合伙 | 用户需求 | 单执行地址 + 链下份额账本 + Safe 保管 |

```
         │            │            │            │             │

         │            │      └─────┬─────┘                    │
         │            │            │                          │
   ┌─────▼────────────▼────────────▼──────────┐   ┌───────────▼────────┐
   │              chain / exec                │   │      monitor       │
   │  RPC · 签名 · 模拟 · 发送 · 确认 · 重试    │   │  TG 告警 · 日报     │
   └──────────────────────────────────────────┘   └────────────────────┘
```

**关键设计决定：策略层只产出「意图」(Intent)，不直接发交易。**
所有 Intent 必须通过 `risk` 闸门，再由 `exec` 串行执行。
好处：dry-run 与实盘共用同一条决策路径，只在 `exec` 末端分叉；
所有被否决的意图都会落日志，便于事后复盘策略而不是复盘交易。

## 4. 核心算法

### 4.1 带宽状态机（strategy/bandwidth.py）

输入：当前时段状态、分时段已实现波动率 σ、事件日历、池的 tickSpacing。
输出：目标区间 `[tick_lower, tick_upper]`。

```
δ_target = clamp( k · σ_seg · √(Δt_rebalance) , δ_min, δ_max )

其中：
  k              安全系数，默认 2.5（约 99% 单期不出界）
  σ_seg          该时段的每小时已实现波动率，EWMA 估计
  Δt_rebalance   预期再平衡间隔（小时）
  δ_min          由 tickSpacing 决定的物理下界，另加安全余量
  δ_max          风控上界

事件覆盖（优先级高于以上计算）：
  美股开盘前 30min           → δ = max(δ_target, 3%)
  财报/宏观事件 ±24h         → δ = max(δ_target, 6%) 或直接空仓
  事件日历拉取失败            → 按「有事件」处理（fail-safe）
  链上价与标的现价偏离 > 阈值  → 暂停开新仓
```

区间**非对称**：以当前 tick 为中心对称，但在事件后跳空方向上留更宽的一侧
（由标的现价与链上价的价差方向决定）。

### 4.2 再平衡决策（strategy/rebalance.py）

触发条件（任一满足即产生 Intent）：
1. 价格距区间边界 < 20% 带宽（预警式提前动，避免真出界）；
2. 已出界（最高优先级）；
3. 时段切换导致 δ_target 与现区间偏离 > 50%；
4. 事件窗口进入/退出。

执行前必须过成本模型：

```
预期收益 = 新份额增量 × 该池每小时奖励预算 × 预计持有小时数
预期成本 = swap 滑点 + 已实现 IL + gas + 对冲调整成本
仅当 预期收益 > 2 × 预期成本 才执行
```

出界时**跳过收益校验**直接执行 —— 出界的机会成本是该小时全部奖励。

### 4.3 份额与奖励密度（campaign/）

```
我的份额_t   = L_mine / L_active(current_tick)     # 均从链上直接读，不依赖第三方
奖励密度_pool = 每小时预算_pool / L_active
uptime      = in-range 小时数 / 总小时数
```

`每小时预算_pool` 在 F2 确认前，同时维护三个假设下的估计值，
并在《规则校准报告》里用首日实际到账数据做最小二乘反推，选中残差最小的假设。

### 4.4 LP delta 与对冲（hedge/）

v3 头寸在区间内持有的标的数量：

```
x(P) = L · (1/√P − 1/√Pb)        Pa ≤ P ≤ Pb
delta_lp = x(P)                   （以标的计价的净多头敞口）
```

对冲腿目标 = `−delta_lp × hedge_ratio`（默认 1.0）。
再对冲触发：`|当前对冲腿 + delta_lp| / |delta_lp| > 10%` 或每次 rebalance 后强制同步。
资金费率计入 `accounting`，若累计对冲成本超过激励收益的 30%，降低 `hedge_ratio` 并告警。

## 5. 安全设计

1. **签名隔离**：策略进程不持有私钥；签名通过独立本地进程，接口只接受白名单目标 + 白名单方法选择器。keystore 与权限为 600/400、未被 Git 跟踪的 `.env` 是互斥密钥来源，明文私钥仅由签名子进程读取。
2. **交易前模拟**：所有交易先 `eth_call`/simulate，回滚即中止并告警。
3. **热钱包最小化**：执行 EOA 只放当轮运行资金，其余在 Safe 多签。
4. **幂等与崩溃恢复**：每个 Intent 有唯一 ID，落盘后再发送；重启时先对账链上实际头寸再决策。
5. **紧急停止**：`log/HALT` 文件存在即拒绝一切写操作（人工可用一条命令刹车）。
6. **配置即合约**：`config/pools.yaml` 中的池地址在启动时做链上校验（token0/token1/fee/tickSpacing），任一不符拒绝启动。

## 6. 运行与调度

- 常驻 asyncio 进程；由 launchd 保活（沿用 `bn-monitor/launchd` 约定）。
- 三个循环：
  - **快循环 15s**：读池价、检查出界、触发紧急再平衡。
  - **慢循环 5min**：波动率更新、带宽重算、对冲检查、跨池评估。
  - **小时循环**：份额与 uptime 结算、奖励密度记录、归因入账、告警汇总。
- `watchdog` 独立进程监控主进程心跳，参考 `bn-ai/watchdog.py`。
