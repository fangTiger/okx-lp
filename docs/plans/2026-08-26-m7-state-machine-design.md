# M7 主状态机设计

## 边界与结构

M7 采用每池一个同步状态机实例。状态机只负责检查顺序、状态推进、广播授权传递、
状态持久化和转移审计，不在策略层重新编码 M5/M6 的交易细节。时段组件、风控闸门、
池价读取、建仓动作、撤出动作都通过可注入协议提供；再平衡必须直接调用 M6
的 `RebalanceOrchestrator.execute()`。这样测试可以注入假时钟与回放价格，实盘接线仍走
既有 Intent、模拟、签名和白名单路径。

每轮严格按 `should_make_market(now)`、风控检查、策略判断的顺序执行。非做市或风控
否决对持仓态拥有最高优先级，转到 `EXITING`；`EXITING` 必须完成 burn、collect 和全部
换回 USDC 后才能回到 `IDLE`。进入、再平衡和撤出动作只有完整成功才推进下一状态，
异常会告警并停留在当前阶段。`run()` 与单步入口的广播参数都默认关闭，只有显式传入
`allow_broadcast=True` 才向下游传播授权。

广播参数按精确布尔类型校验，`1`、字符串等真值一律失败关闭。风控结论另带显式的
`allow_exit`：普通 HALT 或 live 事实阻断默认禁止包括撤出在内的一切写链；只有需要防御
性清仓的熔断结论才显式允许 `EXITING` 继续执行。

## 数据、恢复与审计

`IDLE` 获得入场许可时，以当前 tick 和固定宽度 `0.005` 调用 M1
`aligned_tick_range()`，并把向外对齐的 tick 与对应价格区间一起持久化。持久化使用同目录
临时文件、`fsync` 和原子替换；文件不存在表示首次启动 `IDLE`，损坏或未知状态则拒绝
静默重置。M8 尚未实现链上对账，本次仅保存足够让后续对账使用的本地状态与区间。
`OUT_PENDING` 另外保存首次出界时间与方向，避免重启后重置连续出界计时。三个交易阶段
一旦失败，还会保存失败原因与时间并锁停；
后续循环和进程重启都不会自动重做可能已经部分成功的链上动作，必须等待 M8 对账或
人工处理。

每次实际状态转移追加一行 JSON，至少包含 UTC 时间、旧态、新态、中文触发原因、池价、
当前 tick 和区间上下沿。首次越界立即由 M4 `OutrangeDetector` 开始计时并转到
`OUT_PENDING`；持续界外达到确认时间或保护上限时转到 `REBALANCING`，确认前回归区间
则返回 `IN_RANGE`。

50/50 差额的最小兑换金额放在 `risk.yaml` 的 `swap.min_amount_usd`，默认 1 USD。
差额严格低于阈值直接返回 `None`，恰好达到阈值仍允许兑换。M6 编排器加载并使用同一
阈值，确保 burn、collect 后的余额粉尘不会生成 swap。
